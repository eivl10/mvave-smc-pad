# Протокол M-Vave SMC-PAD (BLE)

Справочник по проводному протоколу устройства. Производитель не документирует ничего;
всё ниже — из публичного реверс-инжиниринга с измерениями на железе.

**Источники:**
- [SDR3078/mvave-home-assistant](https://github.com/SDR3078/mvave-home-assistant) — `docs/HARDWARE-BLE.md`,
  рабочий Python в `custom_components/mvave/devices/smc_pad.py`. Основной источник.
- [SDR3078/mvave-smc-pad-ableton](https://github.com/SDR3078/mvave-smc-pad-ableton) — `docs/HARDWARE.md`,
  измеренная палитра, USB-путь.
- [ZzpsS/m-vave-codex-bridge](https://github.com/ZzpsS/m-vave-codex-bridge) — `src/controllers/smc-pad/lighting.ts`,
  независимое подтверждение формата RGB-записи.

## 1. GATT-карта

| Сервис | Характеристики | Назначение |
|---|---|---|
| `0000ae40-0000-1000-8000-00805f9b34fb` | `0000ae41-…` write-without-response<br>`0000ae42-…` notify | **Вендорский туннель.** Конфигурационная память читается и пишется через него. Именно здесь живёт цвет. |
| `03b80e5a-ede8-4b33-a751-6ce34ec4c700` | `7772e5db-3868-4112-a1a9-f2669d106bf3` read/write-without-response/notify | Стандартный BLE MIDI. Приложение уже его использует для входящих нот и CC. |
| `180f` | `2a19` read/notify | Батарея, один байт 0-100 %. Замер 2026-09-23: читается без сопряжения, notify работает. |
| `180a` | `2a29`, `2a24` read | manufacturer = `sincoaudio` |
| `0000ae00-0000-1000-8000-00805f9b34fb` | `0000ae01-…` write-without-response<br>`0000ae02-…` notify | **Не исследован.** Второй вендорский сервис. ⚠️ Подписка на `AE02` глушит поток MIDI: после неё ноты пэдов перестают приходить (замер 2026-09-23, дважды). Не подписываться. |

**Shift и Note Repeat в эфир не шлют ничего.** Замер 2026-09-23: подписка на MIDI и `AE42`,
Shift ×3, Note Repeat ×3, Shift+Note Repeat ×2, между группами пэд 16 как метка.
Метки (нота 51) пришли все три, между ними — ни байта. Обе кнопки обрабатывает прошивка,
хосту они недоступны; то же для Shift по USB измерено у SDR3078.

Сопряжение на уровне GATT не требуется. MTU 512. Устройство перестаёт анонсироваться,
пока подключено.

**Два канала независимы.** Цвет идёт в `AE41` сырым вендорским фреймом.
Префикс `80 80` (BLE-MIDI timestamp) к нему **не добавляется** — он относится только
к MIDI-характеристике.

## 2. Вендорский фрейм

```
00 59 <cmd> <len LE×3> │ <region> <addr LE×4> <count LE×3> [data…] │ <checksum>
       └─ заголовок ───┘ └──────────── payload ────────────────────┘
```

| Поле | Значение |
|---|---|
| `00 59` | фиксированный вендорский префикс |
| `cmd` | `0x22` = write, `0x23` = read, `0x11` = discovery |
| `len` | длина payload, little-endian, 3 байта |
| `region` | `0x05` = хранилище пресетов, `0x04` = live-состояние |
| `addr` | адрес внутри региона, little-endian, 4 байта |
| `count` | количество байт данных, little-endian, 3 байта |
| `checksum` | `(~sum(payload)) & 0xFF` |

Инвариант для проверки: `(sum(payload) + checksum) & 0xFF == 0xFF`

**ACK** приходит на `AE42`: `00 59 00 01 00 00 00 FF`, задержка ≈410 мс.

Референсная реализация (`smc_pad.py`, дословно):

```python
def vendor_packet(command, region, address, data_or_count) -> bytes:
    payload = bytes((region, *address.to_bytes(4, "little"), *count.to_bytes(3, "little"))) + data
    checksum = (~sum(payload)) & 0xFF
    return bytes((0x00, 0x59, command, *len(payload).to_bytes(3, "little"))) + payload + bytes((checksum,))
```

> **Не портировать `sysex_wrap` / `sysex_unwrap`.** Это упаковка по 7 бит для USB-пути
> (MidiSuite оборачивает вендорский фрейм в SysEx между `F0` и `F7`). По BLE фрейм идёт сырым.

## 3. Карта памяти пресета (region `0x05`)

```
PRESET_SIZE      = 3539     # размер одного слота
PAD_TABLE_OFFSET = 211      # начало таблицы пэдов внутри слота
PAD_RECORD_SIZE  = 26       # 0x1A, шаг записи пэда
PAD_COUNT        = 16
```

Раскладка слота до таблицы пэдов — снята дампом, см. §9:

| Смещение | Содержимое |
|---|---|
| 0–114 | 5 записей кнопок по 23 байта. Байт 2 = CC 25…29, `Led` на +22 |
| 115–210 | 16 записей энкодеров по 6 байт. Байт 2 = CC 30…45 (два банка по 8) |
| 211+ | 16 записей пэдов по 26 байт на каждый банк |

`115 + 96 = 211` — константа `PAD_TABLE_OFFSET` сходится ровно, это не подгонка.

Адрес записи пэда:

```
addr = slot * 3539 + 211 + ((bank - 1) * 16 + record) * 26
```

Внутри 26-байтовой записи:

| Смещение | Поле |
|---|---|
| `+2` | нота пэда |
| `+5` | **RGB**, 3 байта (r, g, b) |
| `+8` | **Led**, 1 байт |

`record = pad_number - 1`. **PAD1 = нижний левый** (нота 36), PAD16 = верхний правый (нота 51).

Для slot 0 / bank 3 адрес RGB схлопывается в константу `0x0418 + record * 0x1A`
(проверка общей формулы: `0 + 211 + (2*16 + 0)*26 + 5 = 1048 = 0x418`).

У кнопок записи по 23 байта, `Led` на смещении `+22`.

## 4. Два режима подсветки

Байт `Led` выбирает режим, и режимы **взаимоисключающие**:

| `Led` | Поведение |
|---|---|
| `0xFF` (заводское, «unarmed») | Показывает поле **RGB, 24 бита**. При физическом нажатии пэд мигает белым и возвращается. **Note On от хоста игнорируется.** Запись RGB отображается сразу. |
| номер ноты («armed») | Показывает цвет из фиксированной палитры по velocity последнего Note On для этой ноты (velocity 0 = выключено). Светом владеет хост. Запись RGB **сохраняется, но не отображается**. |

**Это и есть причина, по которой попытка зажечь пэд через Note On провалилась** —
пэды unarmed, хостовый Note On просто игнорируется.

Палитра (только в armed-режиме) вся пастельная: реально различимы около пяти цветов
плюс белый. Насыщенного красного нет. Опорные точки: 5 зелёный, 15 оранжевый,
21 синий, 24 светло-фиолетовый, 40 белый, 0 выключено.

**Отдельного канала яркости у устройства нет** — ни в палитре, ни через MIDI-канал.
Режима мигания в прошивке тоже нет.

Но в RGB-режиме яркость он и не нужен: **масштабирование компонент работает**,
проверено на железе (см. §9). Заводские пресеты сами так и сделаны — используют
`0xF0` как максимум и промежуточные `0x78`, `0x96`, `0xC8`.

Note Off (`0x80`) игнорируется полностью; гасить надо Note On с velocity 0.

## 5. Live-состояние (region `0x04`)

Чтение 16 байт с адреса 0 отвечает одной нотификацией, реассемблирования не нужно.
Раскладка: `78 00 32 04 00 00 KK 00 01 01 SS BB 00 …`

| Байт | Значение |
|---|---|
| 6 (`KK`) | базовый банк пэдов, 0-индексированный (bank 3 читается как `2`) |
| 10 (`SS`) | слот пресета на дисплее, 0-индексированный |
| 11 (`BB`) | переключатель PAD BANK: 0 = базовый банк, 1 = банк-образ 8 |

Эффективно: `slot = SS`, `bank = 8 if BB == 1 else KK + 1`, ограничить 1..8.

**Зачем это читать, а не хардкодить slot 0 / bank 3:** запись в слот, который не на
дисплее, ложится в память и не отображается. Upstream документирует ровно этот случай.
Для пользователя это неотличимо от «протокол не работает» — молчаливый no-op без ошибки.

## 6. Волатильность

Все записи через вендорский канал — **правки RAM**. Отображаются немедленно, теряются
при передёргивании питания. Публичной команды сохранения в флеш не найдено — как
MidiSuite делает свои правки постоянными, неизвестно.

Практическое следствие: хост переприменяет цвета **на каждом подключении**. Настройка
через MidiSuite не нужна вообще.

## 7. Темп и транспорт

- Фрейм RGB — **18 байт**, влезает даже в минимальный ATT payload 20 байт. Чанкинг не нужен ни при каком MTU.
- Upstream измерил ≈12.5 мс между записями как чистые; 10 полных обновлений сетки в секунду начинают терять пэды. Рабочий запас — **25 мс между фреймами**.
- **ACK ждать не надо** при пакетной записи в пределах ~1 с. 410 мс на запись сделали бы интерактивную смену цвета неработоспособной на ощупь.
- Windows: bleak под капотом использует WinRT и видит оба канала. `python-rtmidi`/`mido` по BLE устройство **не увидят вообще** — RtMidi на винде ходит через WinMM, а BLE MIDI винда отдаёт только через WinRT.
- Кэш GATT винды может не отдать сервис `AE40`, если он не был перечислен при сопряжении. Лечится первым подключением с `winrt={"use_cached_services": False}`.

## 8. Заводская карта устройства

Канал 10, пэды ноты 36-51, энкодеры CC 30-45 (два банка по 8 через кнопку KNOB BNK),
кнопки CC 25-29. Совпадает с тем, что приложение наблюдает на входе.

> Осторожно: `mvave-smc-pad-ableton` описывает ноты 1-16 на канале 1 — это **другой
> пресет** (поставляемый launcher-пресет), а не противоречие. Карта зависит от
> загруженного слота, поэтому её надо читать с устройства, а не предполагать.

## 9. Подтверждено на железе 2026-09-17

Всё ниже снято с реального устройства (SMC-PAD автора) через `tools/probe_color.py`,
а не взято из источников. Где расходится с источниками — верить этому разделу.

### Что подтвердилось

- **Канал работает.** `AE40`/`AE41`/`AE42` присутствуют, запись принимается, на каждый
  фрейм приходит ACK `00 59 00 01 00 00 00 FF`.
- **Адресация верна.** Проверено методом отрицания: записи в конкретные (слот, банк)
  оставили нули в поле RGB **ровно** в затронутых таблицах и ни в одной другой.
  Перебирали банки 1-8 при слоте 0 и слоты 0-7 при банке 3 — обнулилась запись 0
  именно в этих 15 таблицах, остальные 49 сохранили свои цвета.
- **Запись отображается сразу**, без перезагрузки слота и без команды обновления.
- **Запись 0 = нота 36 = нижний левый пэд.** Байт 2 записи читается как `0x24`.
- **Яркость масштабированием RGB работает.** Лесенка `255 → 120 → 48 → 12` на нижнем
  ряду видна глазом как убывание. Уровень 12 ещё светится.

### Структура записи пэда (26 байт)

```
00 09 24 00 7F  FF 00 00  FF  00 00 00 ...
│  │  │  │  │   └─ RGB ─┘  └ Led
│  │  │  │  └ 0x7F — верхняя граница velocity
│  │  │  └ 0x00 — нижняя граница velocity
│  │  └ нота (0x24 = 36)
│  └ канал (0x09 = канал 10)
└ тип: 0x00 у пэдов, 0x02 у кнопок и энкодеров
```

### Ноты по банкам (слот 0)

| Банк | Ноты | Заводской цвет |
|---|---|---|
| 1 | 4–19 | `#96c8f0` |
| 2 | 20–35 | `#f0f000` |
| 3 | 36–51 | `#37e6c9` |
| 4 | 52–67 | `#0000f0` |
| 5 | 68–83 | `#00f000` |
| 6 | 84–99 | `#f00000` |
| 7 | 100–115 | `#00f0f0` |
| 8 | 52–67 (дубль банка 4) | `#7878f0` |

Приложение видит ноты 36-51, то есть работает в банке 3 — сходится с тем, что
блок live-состояния отдаёт `bank=3`.

### Оговорки

- **MTU не 512, а 23.** Источники обещали 512; на этой машине согласовалось 23.
  На запись это не влияет — фрейм RGB 18 байт. Чтения по 104 байта при этом
  проходят нормально: ответ приходит одной нотификацией, стек сам собирает.
  Не закладываться на большой MTU.
- Ответ на чтение — **полный вендорский фрейм**, не голые данные. Разбирать только
  через `read_response_data()`, иначе смещения едут и возвращается правдоподобный
  мусор без всякой ошибки.
- Слот 1 банк 3 и слот 1 банк 8 имеют тип записи `0x04` и осмысленные значения `Led`
  (0x00…0x1F вместо `0xFF`) — это заармленные пэды другого типа. Подтверждает, что
  `Led` действительно переключает режим. Наши слоты и банк такого не используют.
